# Изолированное ядро симулируемого ввода

Цель — Godot 4.4.1. Ядро не подключено к корневой сцене, UI или gameplay. Это внутренний формат игры, не API Моторики. Основания: `contracts/input-v1.schema.json`, `contracts/README.md`, `planning/product.md`. Правила REST/BOTH/восстановления и профиль утверждены Августом 03.11.2026 и согласованы с contracts/README.md. Архитектурный обзор сохранён как историческое предложение; полный текст ТЗ организаторов по-прежнему отсутствует.

## Компоненты

- `input_frame.gd` / `InputFrame`: семь полей существующего InputFrame v1.
- `control_command.gd` / `ControlCommand`: direction, intensity и локальные поля безопасности state, reason, pause_required. Последние не добавляются в сериализованный InputFrame и не объявляются новой версией внешнего контракта.
- `input_config.gd` / `InputConfig`: независимые пары порогов, таймаут, политика восстановления и поведение REST.
- `input_validator.gd` / `InputValidator`: проверка структуры, чисел, source, seq и времени до преобразования в типизированный кадр.
- `input_decoder.gd` / `InputDecoder`: два состояния гистерезиса и аналоговая интенсивность.
- `input_stream_guard.gd` / `InputStreamGuard`: блокировка после ошибки, свежесть и восстановление.
- `manual_input_source.gd` / `ManualInputSource`: программная генерация кадров с последовательным seq и сигналом frame_ready.
- `input_pipeline.gd` / `InputPipeline`: публичная точка интеграции, сигнал command_ready, методы begin_stream, submit, tick, request_resume, suspend.

Зависимости направлены от фасада к компонентам и от компонентов к типам/конфигурации; обратных ссылок на фасад, UI, gameplay и autoload нет. Низкоуровневые decode/materialize/filter предназначены для фасада: игровой модуль должен получать только результат InputPipeline, а не обходить проверку через Decoder.

## Подключение Августом

1. Создать `InputConfig.emulator_profile()` (A/B: on=0.55, off=0.40, heartbeat_ms=50, timeout_ms=250); для независимых порогов доступен `InputConfig.new(on_a, off_a, on_b, off_b)`; создать `InputPipeline.new(config)` и `ManualInputSource.new()`. Конфигурация копируется фасадом; для её изменения создать новый pipeline и заново пройти нейтраль/продолжение.
2. Подключить `pipeline.command_ready` к обработчику команды. Полученный объект считать неизменяемым. Использовать **либо** сигнал, **либо** возвращаемое значение для применения команды, чтобы не обработать её дважды.
3. Установить общий origin локальных монотонных часов; вызвать `source.reset()` и `pipeline.begin_stream("manual_emulator")`. Все timestamp_ms и now_ms ниже — целые миллисекунды **от этого origin**. В живой интеграции их можно получать как `Time.get_ticks_msec() - origin_ms`; при повторяемой симуляции — передавать явно по одному и тому же расписанию. Смешивать время ОС, абсолютные ticks и время потока нельзя.
4. На каждом heartbeat получать `frame = source.sample(elapsed_ms, a, b, connected)` и вызывать `pipeline.submit(frame, received_elapsed_ms)`. Альтернатива — подключить frame_ready к submit через обработчик, который передаст время приёма. Не применять оба способа сразу: один seq поступит дважды и будет безопасно отклонён.
5. **Каждое обновление хоста вызывать `pipeline.tick(now_ms)`, даже если кадров нет и игра приостановлена из-за ввода.** RefCounted не имеет автоматического _process. Иначе ядро не сможет известить о молчании источника. Кадры эмулятора должны поступать периодически и при неподвижных значениях; интервал задаётся `config.heartbeat_ms`, в утверждённом профиле 50 ms. Таймаут также проверяется до приёма каждого кадра и перед resume.
6. При старте/восстановлении после отказа или SUSPENDED подать нейтральный кадр с обоими значениями не выше off, затем вызвать `request_resume(now_ms)`. До этого выдаётся только безопасная остановка. Resume не запоминается на будущее: если последний свежий кадр всё ещё активен, запрос ничего не разблокирует.
7. Для обрыва передавать `connected=false` (источник зануляет каналы) либо перестать вызывать sample, продолжая tick. Для восстановления — connected=true, без сброса seq и времени. Сброс seq допускается только новым begin_stream вместе с reset источника и общим новым origin; пакет не может сам объявить новый поток.
8. На сворачивание/внешнюю паузу вызвать `suspend()`. Хост отвечает за жизненный цикл и паузу игры; возобновление проходит через тот же нейтральный барьер. Хост не должен разрешать gameplay обновляться в фоне при поступлении новых кадров.

Вызовы выполняются последовательно в основном потоке; обработчики command_ready только потребляют результат, не вызывают submit/begin_stream/tick рекурсивно. Корень должен отдельно объединять пользовательскую паузу и блокировку ввода: `pause_required=false` не является приказом автоматически снять пользовательскую паузу. При true он останавливает игровое движение и таймеры; само ядро не управляет узлами игры.

## Поведение и решения безопасности

| Вход/условие | Результат |
|---|---|
| Каналы неактивны | REST, intensity=0, state=REST. pause_required=true: остановка движения и игровых часов; следующая разрешённая OPEN/CLOSE продолжает задачу. |
| Только A / B активен | OPEN / CLOSE, state=ACTIVE, пропорциональная intensity; pause_required=false. |
| Оба активны в разблокированном потоке | BOTH, intensity=0, state=BOTH, reason=opposing_channels, pause_required=true. Действует BOTH-блокировка до свежего нейтрального кадра: один оставшийся зажатым канал даёт WAITING_NEUTRAL/both_requires_neutral. Нейтраль снимает только BOTH-блокировку без resume; следующий активный кадр разрешён. |
| Отключённый валидный кадр | REST/0, state=DISCONNECTED, блокировка и сброс гистерезиса. |
| Ошибка структуры, диапазона, версии, порядка или времени | REST/0, state=INVALID с конкретной reason, блокировка и сброс гистерезиса. Невалидный кадр не продвигает seq/timestamp принятого потока. |
| Кадр старше или равен таймауту / молчание | REST/0, state=STALE, reason=stale_frame или stream_timeout, блокировка и сброс гистерезиса. |
| Каналы зажаты после старта/ошибки | REST/0, state=WAITING_NEUTRAL, pause_required=true. BOTH отображается отдельно, но не отменяет строгую блокировку ошибки. В ожидании reason сохраняет исходную причину отказа. |
| Свежий нейтральный кадр после старта/отказа/SUSPENDED | REST/0, state=WAITING_RESUME. Только явный resume при всё ещё нейтральном свежем кадре снимает блокировку; сам resume не выдаёт движения. |
| Внешняя приостановка | REST/0, state=SUSPENDED, новая блокировка. |

При впервые обнаруженной большой паузе доставки submit сначала публикует STALE, а затем состояние нового кадра, например WAITING_NEUTRAL. Это намеренно: обнаруженный обрыв не скрывается свежим пакетом. tick публикует остановку при истечении таймаута один раз до следующего валидного подключённого кадра, сохраняя причину уже зарегистрированного отказа; его возвращаемое значение всегда является снимком текущего результата. Переданный/полученный объект не является внутренним сохранённым состоянием фасада.

## Настраиваемое и принятое без полного ТЗ

- Стартовый профиль: A/B on=0.55, off=0.40. Для индивидуальной конфигурации пороги задаются независимо; условие `0 <= off < on < 1`. Ширина гистерезиса — `on - off` для каждого канала. Включение при `x >= on`, выключение при `x <= off`.
- Формула интенсивности — `clamp((x - on) / (1 - on), 0, 1)`. Это сохранённая утверждённая формула: выше on сила пропорциональна, в полосе гистерезиса направление сохраняется, но скорость нулевая. Для изменения формулы требуется согласованная правка Decoder, а не отдельная формула в gameplay/UI.
- timeout_ms по умолчанию 250 — утверждённый параметр эмулятора, не медицинский норматив. Граница устаревания включительна (`age >= timeout`). Частота кадров не задана скрытым таймером; её определяет вызывающая сторона.
- Для ошибок/старта/SUSPENDED разрешена только RecoveryPolicy.NEUTRAL_AND_RESUME. Прежний вариант NEUTRAL_ONLY отклоняется при валидации конфигурации; нейтраль без resume снимает только отдельную BOTH-блокировку. Варианта автоматического возобновления на зажатых каналах нет. Нейтраль проверяется по обоим off-порогам, а не только по декодированному REST после сброса памяти.
- rest_pauses=true — утверждённое обязательное поведение; false отклоняется при валидации. BOTH и ошибки также требуют паузы. Удержание/отпускание детали, оценочные окна и таймеры не реализуются в ядре.
- seq строго возрастает; timestamp не убывает (равные миллисекунды допускаются при разных seq). Пропуски seq допустимы. Будущие timestamp отвергаются: симулятор и фасад используют одну временную шкалу. Возраст проверяется относительно времени создания кадра, а не только момента доставки, поэтому повтор старого времени с новым seq не поддерживает поток бесконечно.
- Для JSON-чисел целочисленные float принимаются только до 2^53−1, затем приводятся к int; bool не принимается за число. NaN/Infinity, неизвестные/лишние поля, неизвестный source и ненулевые каналы disconnected отвергаются. При typed InputFrame значения проверяются заново, поэтому изменение его полей не обходит валидатор.
- Ручной source всегда manual_emulator. Фасад может быть явно запущен для source=replay по существующему контракту; отдельный проигрыватель файлов не входит в эту задачу. Повторяемая симуляция доступна через reset + одинаковые значения и времена sample/submit/tick/resume. Никакого графического или клавиатурного источника здесь нет.

Августу остаётся подключить фасад к UI Антона и механике Димы. REST/BOTH/отказ не создают штрафов или событий action_failed; метрики не реализованы. Для BOTH UI использует reason=opposing_channels как основание мягкого объяснения; текст и экран в ядре не создаются. При ожидании после отказа state описывает текущий барьер, а reason сохраняет причину отказа до resume либо нового отказа. Переназначение каналов из будущего профиля, хранилище, метрики и сессии не реализованы: здесь A→OPEN, B→CLOSE по принятому продукту.
