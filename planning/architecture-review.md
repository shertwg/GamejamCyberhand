# Архитектурный обзор «Орбитальная мастерская: Последний свет»

Дата: 03.11.2026. Область: локальный checkout команды shertwg, Godot 4.4.1. Это обзор и предложение порядка интеграции, а не изменение задач или утверждение требований организаторов.

Обозначения: **Факт** — содержимое файлов или результат чтения состояния checkout; **Предложение** — решение для обсуждения Августом; **Неизвестно** — в изученных файлах нет достаточного подтверждения. Ссылки вида `путь:строка` относятся к состоянию на момент обзора.

## 1. Краткий вывод

**Факт.** Репозиторий содержит организационную подготовку и минимальный Godot-каркас, но ещё не игровое MVP. Единственная сцена `game/main.tscn:1–6` подключает `game/main.gd`, который создаёт два текстовых элемента и прямо назван временной заглушкой (`game/main.gd:3–25`). В `game/core/`, `game/ui/`, `game/gameplay/`, `game/content/` обнаружены только `.gitkeep`.

**Факт.** Принятый командой сценарий — автоматический маршрут магнитного захвата, A→открытие, B→закрытие, аналоговая интенсивность действия, tutorial, три уровня и адаптация (`planning/product.md:5–22,29`; `planning/assignments.md:7,99–105`). Это два аналоговых канала противоположных команд, а не отдельный канал направления и отдельный канал силы: такое прочтение следует из указанных документов и должно быть закреплено капитаном до реализации. Подтверждения этой схемы полным ТЗ организаторов нет (`planning/requirements.md:3,22–26`).

**Предложение.** Сохранить один проект в корне и один композиционный корень Августа; соединять небольшие модули сигналами/методами, без общей глобальной шины и новых обязательных autoload. Сначала закрепить интерфейсы и безопасный ввод, затем собрать один сквозной цикл «сигнал → действие → событие → итог», после него подключить полный tutorial, три конфигурации уровня и адаптацию. Последние остаются обязательной частью командного MVP, а не отложенным расширением.

**Граница достоверности.** В этой работе выполнялось только чтение файлов и состояния Git, затем создание данного документа. Godot, тесты, сборки, APK и скрипт подготовки веток не запускались. ## 3. Предлагаемая архитектура MVP и поток данных

**Основание:** направление потока уже описано в `contracts/README.md:5–14` и `planning/AI_PROJECT_CONTEXT.md:21`. Ниже — минимальная реализационная декомпозиция для утверждения; перечисленные модули пока не созданы.

```text
Панель эмулятора / клавиши разработки / трасса
                       ↓
InputSource → InputFrame → проверка и Decoder → ControlCommand
                                                  ↓
                           управление сессией → Gameplay
                                                  ↓
                                              GameEvent
                                                  ↓
                                  сборщик метрик → SessionSummary
                                                  ↓
                                              UI / LocalStore

UI start/pause/resume/retry/exit → управление сессией
Валидность/свежесть ввода → управление сессией → пауза Gameplay
Кадр, пороги, команда, состояние сессии → UI только для отображения
```

1. **Композиционный корень — Август.** Существующие `game/main.tscn` и `game/main.gd` становятся местом создания/подключения модулей. Корень связывает сигналы, а не содержит всю механику. Один активный источник на сессию; смена источника — явное действие со сбросом состояния декодера. Не вводить autoload без конкретной необходимости.
2. **Источник и нормализация — core.** Ручной эмулятор и replay производят одинаковый InputFrame v1 с `schema_version`, `seq`, `timestamp_ms`, двумя значениями, `connected`, `source` (существующая schema `contracts/input-v1.schema.json:6–18`). Частота поступления кадров независима от изменений ползунка: неподвижный сигнал тоже должен давать heartbeat, иначе исправный эмулятор попадёт в таймаут.
3. **Валидация и Decoder — core.** Проверяют кадр/порядок/свежесть, ведут два независимых состояния гистерезиса, выдают только REST/OPEN/CLOSE/BOTH и intensity. Состояние исправности потока передаётся отдельно координатору и UI: нельзя обозначить обрыв только REST, иначе он неотличим от исправного покоя.
4. **Координатор сессии — core.** Владеет start/pause/resume/retry/exit, идентификатором сессии и разрешением игрового обновления. Различает пользовательскую паузу, фон и блокировку ввода. UI не снимает блокировку невалидного потока простым resume. Корень подключает его к жизненному циклу приложения.
5. **Gameplay — Дима.** Одна механика захвата, автоматический маршрут, tutorial и три конфигурации отдельно от сцены. Принимает команды и состояние паузы, управляет попыткой и игровым временем, выдаёт события с причинами. Интенсивность меняет скорость открытия/закрытия; никакой прямой зависимости от UI или Input API (`planning/team/dima.md:10–16`).
6. **Адаптация — внутри gameplay, владелец Дима.** Минимум: один изменяемый параметр, например ширина окна; ограниченные шаги после серий успехов/ошибок, применение между попытками. Не менять пороги ввода, не подстраивать параметры посреди текущей попытки. Конкретные серии, шаги, пределы и политика сброса пока неизвестны. Передавать наружу причину и прежнее/новое значение для UI и фиксации условий результата. Это уточнение реализации задачи, а не передача её ядру.
7. **Метрики — core.** Gameplay сообщает факты, core агрегирует их один раз по event_id и только для текущих session_id/attempt_id. Успешность, время BOTH и удержания вычислять по определениям `contracts/README.md:18–21`; нулевые знаменатели и отсутствующая реакция дают null. Для времени удержания/оценочных окон и начала видимой подсказки текущего перечня событий недостаточно: Август и Дима должны согласовать необходимые данные/сигналы. Не вычислять метрики по текстам UI или частоте перерисовки.
8. **UI и контент.** UI отображает состояние каналов, команду, подсказки, параметры адаптации и готовую сводку; отправляет навигацию либо значения в эмуляторный адаптер. Tutorial-сценарий и условия прохождения — Дима; отображение — Антон; короткие фразы/ID — Арина, импортирует Август (`planning/team/anton.md:10–14`; `planning/team/dima.md:13`; `planning/team/arina.md:11–13`; `planning/tasks.md:23`).
9. **LocalStore — core.** Версионированные пороги, настройки стороны и принятый прогресс, безопасные значения по умолчанию при отсутствии/повреждении файла (`planning/team/august.md:14`). Для MVP не нужен сервер или база данных; точный локальный формат выбирает Август. Не сохранять каждый входной кадр как обязательную пользовательскую историю.

**Предложение к общему интерфейсу:** зафиксировать точные сигнатуры приёма кадра/команды, навигации и событий; тип данных (например, согласованные GDScript-структуры/объекты); единицы времени; порядок доставки за игровой шаг; единственного владельца каждого таймера. JSON-примеры служат образцами данных, но не требуют JSON-сериализации между узлами на каждом кадре. UI и gameplay получают ссылки/сигналы от корня, не ищут друг друга по абсолютным NodePath.

## 5. Безопасная обработка ввода и симуляция

**Факт:** независимый гистерезис, REST/BOTH с intensity=0, A→OPEN, B→CLOSE, предварительный таймаут 250 ms и пауза при потере связи уже описаны (`contracts/README.md:8–11`). Реализации нет. Формула интенсивности, границы сравнения и восстановление описаны недостаточно точно.

**Предложение для утверждения Августом и Димой:**

| Ситуация | Команда и игровое поведение |
|---|---|
| Исправный поток, оба канала неактивны | REST, intensity=0. Открытие/закрытие остановлено, положение захвата и деталь сохраняются; автоматический маршрут может продолжаться в активной сессии. REST не означает потерю потока или автоматическое отпускание детали. |
| Только A / только B активен | OPEN / CLOSE; пропорциональная скорость по intensity. Отпускание детали должно следовать механике раскрытия, а не исчезновению пакета. |
| Оба активны | BOTH, intensity=0; остановить раскрытие/закрытие и маршрут, сохранить деталь. Не превращать это в приоритет более сильного канала и не усреднять сигналы. Показать причину. После выхода пересчитать команду по свежему кадру, без накопленного движения. |
| connected=false | Немедленно сбросить состояния гистерезиса и команду в REST/0, отдельно сообщить «нет сигнала», приостановить движение и игровые таймеры. Ненулевые каналы в таком кадре — нарушение schema; не использовать их. |
| Нет нового валидного кадра 250 ms | Тот же безопасный сброс и блокировка. Watchdog работает независимо от обработчика новых кадров, иначе молчащий источник не будет обнаружен. 250 ms — предварительное командное значение, не норматив и не измеренный результат. |
| Неверная версия/source/тип, отсутствующие поля, NaN/Infinity, значения вне 0..1 | Не выдавать рабочую команду и не маскировать ошибку молчаливым clamp. Безопасный сброс/пауза и отдельная причина. Ограничивать пользовательский ползунок до 0..1 допустимо до формирования кадра; готовый невалидный кадр должен быть отвергнут. |
| Дубликат/убывание seq, откат времени, устаревший кадр | Не продолжать прежнюю активную команду и не освежать watchdog таким кадром; сбросить в безопасное состояние. Правила новой последовательности при смене источника задаёт координатор, а не входной пакет. |
| Фон приложения, retry, смена источника | Очистить активную команду и накопленное время шага. При retry новый attempt_id; поздние события старой попытки игнорировать. После фона/потери связи — свежий валидный нейтральный кадр и явное продолжение, без автозахвата при возврате. |

Для BOTH предлагается заморозить таймер действия/маршрута, но продолжать отдельно учитывать длительность BOTH, если до конфликта открыто оценочное окно. Иначе пауза полностью скроет нежелательную совместную активацию. Намеренный BOTH tutorial не входит в ошибку; пользовательская пауза и потеря связи не дают штрафных попыток. Определения active_ms и scored_window_ms в этом режиме ещё нужно закрепить: существующие документы задают метрику, но не полную модель часов (`contracts/README.md:14,19`; `planning/product.md:22`).

Для каждого канала предлагается `0 ≤ off < on < 1`: включение при `x ≥ on`, выключение при `x ≤ off`, между ними сохраняется прежнее состояние. Для активного единственного канала кандидат формулы — `clamp((x - on) / (1 - on), 0, 1)`. Выше on интенсивность растёт линейно, но в полосе гистерезиса направление ещё активно при нулевой скорости. Это явно обсуждаемое следствие, не утверждённый алгоритм; Август должен выбрать формулу и объяснить её UI/Диме до подключения. Настройки с некорректными порогами отклоняются, а не вызывают деление на ноль. Основание требований — `contracts/README.md:10–11`, точной формулы там нет.

Время InputFrame определено от начала потока (`contracts/README.md:8`). Предлагается единый локальный монотонный отсчёт адаптера и время приёма в core: нельзя напрямую вычитать timestamp потока из системного времени. Проверять последовательность и соответствие временной шкалы текущему запуску источника; watchdog обновлять только после валидного свежего кадра. Replay должен подавать кадры по относительному расписанию, а не всей пачкой. Новый запуск replay явно сбрасывает контекст последовательности. Порог допустимого опережения, частота кадров и правила одинаковых timestamp пока не определены.

**Симуляция для демонстрации (предложение):** два независимых аналоговых регулятора в подписанной панели «Эмулятор», переключатель соединения и выбор воспроизводимой трассы. Панель Антона отправляет значения адаптеру Августа; адаптер формирует InputFrame и подаёт его в тот же валидатор/декодер. Клавиши ПК могут менять эти значения только внутри адаптера разработки. В релизном игровом пути не должно быть второго обходного канала управления.

Набор будущих трасс: чистый A, чистый B, ступени интенсивности одного канала, REST, BOTH, дрожание вокруг обоих порогов, connected=false, полное прекращение кадров, некорректный/повторный/запоздалый кадр и восстановление. Первые сценарии поручены Августу (`planning/team/august.md:13`), ошибки/возврат предусмотрены QA (`qa/manual-cases.md:9–17`). Для демонстрации повторяемости фиксировать пороги, конфигурацию уровня, стартовое состояние и расписание; адаптацию также сбрасывать в известное состояние. Готовых трасс в репозитории пока нет; здесь они не создавались и не исполнялись.
